ЭТАП 11: ВИЗУАЛИЗАТОР ТРАФИКА — ВТОРОЙ СИГНАТУРНЫЙ МОМЕНТ
ПРОЕКТ: Zapret Manager — десктопное приложение для управления

═══════════════════════════════════════════════════════════════════════

🎯 ЦЕЛЬ ЭТАПА

Создать второй сигнатурный момент приложения — живой визуализатор
трафика, который выглядит как «пульт управления космическим
кораблём» или приборная панель хакера. Пользователь видит в
реальном времени:
  • Входящий и исходящий трафик (байты/сек) — два живых графика
  • Пинг до ключевых сервисов (Discord, YouTube, Google,
    Outlast Trials) — линии с цветовой градацией
  • Пропускную способность текущей стратегии (обход DPI работает
    / не работает)
  • Активные соединения (количество TCP-соединений)
  • Карту мира с точками серверов, к которым идёт трафик
    (опционально, но добавляет «вау»-эффект)

После этого этапа пользователь сможет:
  • Открыть страницу «Монитор» (новая страница в Sidebar)
  • Видеть живой график трафика (60 FPS, 60 fps!)
  • Видеть пинг в реальном времени с цветовой градацией
  • Видеть счётчики: загружено, отдано, пакеты, соединения
  • Наблюдать за «здоровьем» обхода — если трафик упал, это
    видно сразу
  • Экспортировать снимок графика (PNG) — бонус

Это второй сигнатурный момент. Если на Этапе 10 пользователь
показывал другу «смотри какие у меня карты», то на Этапе 11 он
скажет «смотри, у меня тут как в NASA». Здесь критично:
  • 60 FPS при 60 обновлениях в секунду
  • Точность данных (реальный трафик, а не моковые значения)
  • Красота (свечение, градиенты, плавные переходы)
  • Информативность (не только «красиво», но и «полезно»)

🏗️ ЧАСТЬ 1: АРХИТЕКТУРНЫЕ РЕШЕНИЯ (обосновать перед реализацией)

【 РЕШЕНИЕ 1: Сбор трафика через sysinfo + winapi, не через WinDivert 】

ОБОСНУЙ:
  • WinDivert — это то, что использует сам zapret для
    перехвата. Использовать его для мониторинга —
    конфликт ресурсов.
  • sysinfo (уже в Cargo.toml с Этапа 1) даёт NetworkData:
    - total_received, total_transmitted (байты с запуска ОС)
  • Для per-process: sysinfo::Process::disk_usage?
    Нет, для сети — нужно через winapi GetExtendedTcpTable
    или IP Helper API.
  • Для скорости (байт/сек) — брать дельту между двумя
    сэмплами:
    delta_bytes / delta_time_seconds

РЕАЛИЗАЦИЯ:
  • Rust-команда get_network_stats() → NetworkStats:
    - bytesIn: u64 (всего получено за сессию приложения)
    - bytesOut: u64 (всего отдано)
    - speedIn: u64 (байт/сек сейчас)
    - speedOut: u64 (байт/сек сейчас)
    - packetsIn, packetsOut: u64
    - connections: u32 (активные TCP-соединения)
    - timestamp: u64

ПОЧЕМУ НЕ WINAPI НАПРЯМУЮ:
  • sysinfo — кроссплатформенный, проще
  • Достаточно для наших целей
  • Winapi оставить для задач, где без него не обойтись
    (ShellExecuteEx на Этапе 6)

ПОЧЕМУ НЕ ETW (Event Tracing for Windows):
  • Избыточно
  • Требует admin-прав
  • Сложно

ПОЧЕМУ НЕ WIRESHARK / PCAP:
  • Требует драйвер
  • Тяжело
  • Не для production-утилиты

【 РЕШЕНИЕ 2: Обновление данных 10 раз в секунду, отрисовка 60 FPS 】

ОБОСНУЙ:
  • Данные о трафике — от ОС, обновляются редко
  • Нет смысла запрашивать чаще 10 раз/сек (100ms)
  • Отрисовка — 60 FPS через requestAnimationFrame
  • Между сэмплами — интерполяция для плавности
  • Это стандарт для системных мониторов (htop, btop, Task
    Manager)

ПОЧЕМУ НЕ 60 РАЗ/СЕК ОПРОС:
  • Каждый вызов sysinfo — системный вызов, нагрузка
  • 10 раз/сек достаточно для восприятия «реального
    времени»

ПОЧЕМУ НЕ 5 РАЗ/СЕК:
  • Заметны «скачки» на графике
  • 10 раз/сек — плавно

РЕАЛИЗАЦИЯ:
  • Rust-команда вызывается из frontend каждые 100ms
  • Или Rust-команда сама emit'ит события каждые 100ms
    (лучше — не блокирует frontend)
  • Frontend хранит буфер последних 60–120 значений
  • Отрисовка через Canvas с requestAnimationFrame

【 РЕШЕНИЕ 3: Отрисовка графика через Canvas 2D, не SVG ]

ОБОСНУЙ:
  • Canvas — 60 FPS при 120+ точках без проблем
  • SVG при 120+ точках начинает тормозить (много DOM-узлов)
  • Canvas даёт полный контроль над пикселями:
    - Градиенты
    - Свечение (shadowBlur)
    - Плавные кривые (bezier)
  • Для статичных спарклайнов (Этап 9) — SVG ок
  • Для живых графиков — Canvas обязателен

ПОЧЕМУ НЕ RECHARTS / VISX / D3:
  • Все они используют SVG под капотом (или Canvas, но
    тяжёлый API)
  • Избыточны для линейного графика
  • +100–200 KB в бандл
  • Меньше контроля над визуалом

ПОЧЕМУ НЕ WEBGL / THREE.JS:
  • Overkill для 2D-графика
  • Тяжело для простого тренда

РЕАЛИЗАЦИЯ:
  • Компонент TrafficCanvas с useRef<HTMLCanvasElement>
  • useEffect с requestAnimationFrame
  • На каждом кадре:
    - Очистить canvas
    - Нарисовать сетку (grid)
    - Нарисовать градиентную заливку под линией
    - Нарисовать линию трафика (сглаженную)
    - Нарисовать точку в конце (текущее значение)
  • Данные — из ref (не state), чтобы не ре-рендерить
    компонент

【 РЕШЕНИЕ 4: Разделение inbound / outbound на два графика или один 】

ОБОСНУЙ:
  • Вариант A: два отдельных графика (сверху — входящий,
    снизу — исходящий)
    - Плюсы: чётко видно оба потока
    - Минусы: занимает много места
  • Вариант B: один график с двумя линиями разного цвета
    - Плюсы: компактно, сравнимо
    - Минусы: при пересечении — путаница
  • Вариант C: один график с заливкой + линия (входящий
    основной, исходящий тонкой линией)
    - Плюсы: визуально чисто
    - Минусы: исходящий менее заметен

РЕКОМЕНДАЦИЯ: Вариант A — два графика друг под другом.
  • Входящий (зелёный, accent-primary)
  • Исходящий (голубой, accent-secondary)
  • Одинаковые масштабы по X (время)
  • Разные масштабы по Y (обычно inbound >> outbound)

ПОЧЕМУ ТАК:
  • Стандарт для системных мониторов
  • Чётко видно оба потока
  • Не путается

【 РЕШЕНИЕ 5: Сглаживание графика через Catmull-Rom или линейную интерполяцию 】

ОБОСНУЙ:
  • Сырые данные — «рваные» (пики, спады)
  • Сглаживание через кривые Catmull-Rom → плавная линия
  • Или через взвешенное скользящее среднее (EWMA) на
    данных

РЕКОМЕНДАЦИЯ: EWMA на данных + линейная интерполяция при
отрисовке.
  • EWMA (α = 0.3): smoothed[i] = 0.3 * raw[i] + 0.7 *
    smoothed[i-1]
  • Меньше «дёрганья», но всё ещё реагирует на изменения
  • Просто, быстро

ПОЧЕМУ НЕ CATMULL-ROM:
  • Может давать «overshoot» (линия выходит за пределы
    данных)
  • EWMA достаточно

【 РЕШЕНИЕ 6: Автомасштабирование по Y (динамический максимум) 】

ОБОСНУЙ:
  • Трафик может быть 10 KB/s или 100 MB/s
  • Жёсткий максимум → либо мелкий график, либо обрезка
  • Автомасштаб: Y_max = max(values) * 1.2
  • Плавное изменение максимума (не рывками)

РЕАЛИЗАЦИЯ:
  • currentMax обновляется через useRef
  • Если новое значение > currentMax → currentMax = newMax
  • Плавно снижается обратно (если трафик упал) через
    линейную интерполяцию

ПОЧЕМУ ПЛАВНО:
  • Резкое изменение Y_max → график «прыгает»
  • Плавное → визуально приятно

【 РЕШЕНИЕ 7: Сетка (grid) и подписи осей 】

ОБОСНУЙ:
  • Горизонтальные линии через 25%, 50%, 75% высоты
  • Вертикальные линии каждые 10 секунд
  • Подписи Y: 0, max/2, max (с форматированием: «1.2 MB/s»)
  • Подписи X: -60s, -40s, -20s, now

ПОЧЕМУ НЕ БЕЗ СЕТКИ:
  • Нельзя оценить значения
  • Не профессионально

ПОЧЕМУ НЕ СЛИШКОМ МНОГО ЛИНИЙ:
  • Визуальный шум

【 РЕШЕНИЕ 8: Пинг до сервисов — линии + текущее значение + история 】

ОБОСНУЙ:

ПОЧЕМУ 4 СЕРВИСА:
  • Discord, YouTube — основные кейсы

【 1. src-tauri/src/commands/monitor.rs (создать) 】
Назначение: сбор метрик трафика.

Структуры:
  • NetworkStats (Serialize, camelCase):
    - bytesIn: u64
    - bytesOut: u64
    - speedIn: u64 (байт/сек)
    - speedOut: u64 (байт/сек)
    - packetsIn: u64
    - packetsOut: u64
    - connections: u32
    - timestamp: u64 (Unix ms)

Команды:
  • get_network_stats() -> Result<NetworkStats, AppError>
    Логика:
    1. Прочитать sysinfo::Networks::refresh()
    2. Просуммировать received/transmitted по всем
       интерфейсам
    3. Сравнить с предыдущим сэмплом (сохранён в
       Mutex<State>)
    4. Вычислить speedIn/speedOut = delta_bytes /
       delta_time_sec
    5. Получить количество соединений через
       GetExtendedTcpTable (winapi) ИЛИ через
       netstat-подобный вызов (медленно)
    6. Вернуть NetworkStats

  • start_monitoring(app: AppHandle, interval_ms: u64)
    -> Result<(), AppError>
    Логика:
    1. tokio::spawn
    2. Loop: каждые interval_ms
    3. invoke get_network_stats → emit "network-stats" в
       frontend
    4. При ошибке — emit "network-error"
    5. Остановка при unmount frontend (через
       stop_monitoring)

  • stop_monitoring(state: State<MonitorState>)
    -> Result<(), AppError>
    Логика:
    • Установить флаг stop в MonitorState
    • Дождаться завершения tokio task

Состояние:
  • MonitorState:
    - prev_sample: Arc<Mutex<Option<(u64, u64, u64)>>>
      (bytesIn, bytesOut, timestamp)
    - stop_flag: Arc<AtomicBool>
    - is_running: Arc<AtomicBool>

Вспомогательные функции:
  • count_tcp_connections() -> u32
    - Через winapi GetExtendedTcpTable
    - Или через sysinfo, если доступно
  • calculate_speed(prev, curr) -> (u64, u64)

Требования:
  • Все команды — async
  • Ошибки через AppError
  • Логирование через tracing (debug, не info — иначе
    зальём лог)
  • Никаких unwrap() без обоснования

【 7. src/hooks/useNetworkMonitor.ts (создать) 】
Назначение: подписка на события network-stats + буфер.

Состояние (ref, не state):
  • bufferRef: useRef<TrafficPoint[]> — последние 120 точек
  • latestRef: useRef<NetworkStats | null> — последний сэмпл
  • isPaused: useState(false) — для UI
  • connectionCount: useState(0) — для UI (обновляется редко)

Методы:
  • start(): Promise<void>
    - invoke("start_monitoring", { intervalMs: 100 })
    - Подписка на "network-stats"
    - При каждом событии:
      • latestRef.current = event.payload
      • bufferRef.current.push({...})
      • Если буфер > 120 — сдвинуть
      • Если isPaused — не обновлять
  • stop(): Promise<void>
  • togglePause(): void

Возвращает:
  • { latest: NetworkStats | null, buffer: TrafficPoint[],
    isPaused, togglePause, start, stop, connectionCount }

Требования:
  • Cleanup listen при unmount
  • Cleanup stop_monitoring при unmount
  • При document.hidden — пауза (опционально)
  • Не хранить данные в useState (только ref)

⚠️ ЧАСТЬ 5: ЧТО МОЖЕТ СЛОМАТЬСЯ (гипотезы)
═══════════════════════════════════════════════════════════════════════

ГИПОТЕЗА 1: sysinfo не даёт per-interface данные
  ПРИЧИНА: API меняется между версиями.
  ЧТО ПРОВЕРИТЬ: использовать Networks::list() и суммировать
    по всем интерфейсам. Или фильтровать Wi-Fi/Ethernet,
    игнорируя loopback.

ГИПОТЕЗА 2: Первый сэмпл даёт неправильный speedIn
  ПРИЧИНА: prev_sample = None → дельта = всё с начала ОС.
  ЧТО ПРОВЕРИТЬ: при первом вызове speedIn = 0, сохранить
    prev_sample, вернуть 0.

ГИПОТЕЗА 3: Canvas тормозит при 120 точках
  ПРИЧИНА: сложные path с тенями.
  ЧТО ПРОВЕРИТЬ: простой stroke без shadowBlur, или
    уменьшить количество точек.

ГИПОТЕЗА 4: DevicePixelRatio даёт размытый canvas
  ПРИЧИНА: canvas.width / canvas.height не учтён DPR.
  ЧТО ПРОВЕРИТЬ: canvas.width = width * DPR; ctx.scale(DPR,
    DPR).

ГИПОТЕЗА 5: requestAnimationFrame накапливается
  ПРИЧИНА: нет cancel в cleanup.
  ЧТО ПРОВЕРИТЬ: useRef<number> для rAF id, cancelAnimationFrame
    в return.

ГИПОТЕЗА 6: Монитор продолжает работать при уходе со страницы
  ПРИЧИНА: stop_monitoring не вызывается.
  ЧТО ПРОВЕРИТЬ: useEffect cleanup в Monitor.tsx.

ГИПОТЕЗА 7: get_network_stats блокирует UI
  ПРИЧИНА: синхронная команда, 10 раз/сек.
  ЧТО ПРОВЕРИТЬ: async команда, tokio task.

ГИПОТЕЗА 8: Mutex дедлок
  ПРИЧИНА: prev_sample Mutex держится через await.
  ЧТО ПРОВЕРИТЬ: короткие блокировки.

ГИПОТЕЗА 9: Пинг до Outlast Trials всегда timeout
  ПРИЧИНА: домен неверный или недоступен.
  ЧТО ПРОВЕРИТЬ: использовать steampowered.com как прокси
    (игра использует Steam).

ГИПОТЕЗА 10: При паузе буфер продолжает заполняться
  ПРИЧИНА: флаг isPaused не проверяется.
  ЧТО ПРОВЕРИТЬ: if (isPaused) return в обработчике событий.

ГИПОТЕЗА 11: При resize canvas не перерисовывается
  ПРИЧИНА: нет ResizeObserver.
  ЧТО ПРОВЕРИТЬ: ResizeObserver на контейнере.

ГИПОТЕЗА 12: Автомасштаб «прыгает»
  ПРИЧИНА: currentMax = max(buffer) каждый кадр.
  ЧТО ПРОВЕРИТЬ: плавное изменение через useRef +
    интерполяцию.

ТРИ БАГА, НАЙДЕННЫХ ЖИВЫМ ЗАПУСКОМ (из этапов 5 и 7):

  1. Логи не появлялись. `startLogsFlusher()` был написан, но никогда
     не вызывался: записи копились в `pendingBatch` и попадали в список
     только пачками по 50 штук. Страница Логи всегда показывала
     «Логи пусты». Исправлено: флашер запускается в App, а таймер
     трогает стор только когда есть что переносить — иначе он
     перерисовывал бы список 10 раз в секунду.

  2. Пересканирование стирало состояние запущенной стратегии.
     `setStrategies` заменял массив целиком, и у новых объектов статус
     снова становился idle. Итог: запустил стратегию, ушёл на другую
     страницу, вернулся — бейдж «Запущена» исчез, кнопка «Остановить»
     стала «Запустить», хотя процесс ещё работал. Исправлено: при
     повторном скане сохраняются status, pid, error и lastRun для тех
     id, которые остались на диске.

  3. Монитор не начинал сбор после монтирования. Подписка и старт были
     разведены по двум эффектам: в StrictMode эффект монтируется,
     cleanup останавливает сбор, а повторный старт блокировался флагом
     `startedRef`. Итог: счётчики замирали на первом сэмпле.
     Исправлено: подписка, таймер, старт и остановка живут в одном
     эффекте.
