🎯 ЦЕЛЬ ЭТАПА

Создать полноценную страницу Logs с виртуализированным списком
(10 000+ строк без лагов), автоскроллом, панелью фильтров
(уровень, источник, стратегия, поиск), экспортом в файл,
цветовой дифференциацией и моноширинным шрифтом. Страница
должна плавно работать при потоке логов 100+ строк/сек.

После этого этапа пользователь сможет:
  • Видеть все логи в реальном времени
  • Прокручивать 10 000+ строк без просадки FPS
  • Включить/выключить автоскролл (следование за новыми
    логами)
  • Фильтровать по уровню (info/warn/error/success/debug)
  • Фильтровать по источнику (system/strategy/user/vpn)
  • Искать по тексту (регистронезависимо, подсветка)
  • Экспортировать отфильтрованные логи в файл
  • Копировать отдельные строки по клику
  • Очистить все логи

Это самая «горячая» страница приложения. Если она тормозит —
всё приложение воспринимается как тормозное. Поэтому
виртуализация и батчинг обновлений критичны.

🏗️ ЧАСТЬ 1: АРХИТЕКТУРНЫЕ РЕШЕНИЯ (обосновать перед реализацией)
═══════════════════════════════════════════════════════════════════════

【 РЕШЕНИЕ 1: Виртуализация через @tanstack/react-virtual 】

ОБОСНУЙ:
  • 10 000 DOM-узлов = 500+ MB памяти и лаги
  • Виртуализация рендерит только видимые строки (~30)
  • @tanstack/react-virtual — современный, лёгкий (5 KB),
    работает с динамической высотой
  • Поддерживает overscan (рендерит 5 строк сверху/снизу
    для плавности)
  • Работает с любым контейнером
  • Не требует измерения высоты для простых случаев

ПОЧЕМУ НЕ react-window:
  • Старее, менее гибкий
  • Нет встроенной поддержки dynamic sizes
  • Меньше обновляется

ПОЧЕМУ НЕ react-virtuoso:
  • Больше по размеру (30 KB)
  • Избыточен для нашего случая

ПОЧЕМУ НЕ СВОЯ ВИРТУАЛИЗАЦИЯ:
  • 500+ строк кода
  • Легко ошибиться с overscan, scroll position
  • @tanstack/react-virtual — проверено в production

ВАЖНО:
  • Установить: pnpm add @tanstack/react-virtual@3.11.2
  • Высота строки фиксирована (24px) — это упрощает
    виртуализацию и ускоряет рендер
  • Перенос строк (word-wrap) НЕ используем — иначе высота
    станет динамической и виртуализация замедлится
  • Длинные строки обрезаются с ellipsis + tooltip при hover

【 РЕШЕНИЕ 2: Логи читаются из useLogsStore, не из локального state 】

ОБОСНУЙ:
  • useLogsStore уже создан на Этапе 4 с батчингом
  • Страница Logs — просто view поверх стора
  • Не дублировать логи в локальном useState
  • Селектор useFilteredLogs (мемоизация) возвращает
    отфильтрованный список

ПОЧЕМУ НЕ ЛОКАЛЬНЫЙ STATE:
  • Логи приходят извне (события Tauri)
  • При переключении страниц локальный state потеряется
  • Стор — единый источник правды

【 РЕШЕНИЕ 3: Фильтры — в useLogsStore, не в локальном state 】

ОБОСНУЙ:
  • Фильтры — часть состояния логов
  • Сохраняются при переключении страниц
  • Один источник правды
  • Если пользователь ставит «только error» — фильтр
    остаётся, даже если он ушёл на Dashboard и вернулся

ПОЧЕМУ НЕ ЛОКАЛЬНЫЙ STATE:
  • При переключении страниц фильтр сбросится
  • Раздражает пользователя

НЕ PERSIST:
  • Фильтры НЕ сохраняем в localStorage — при перезапуске
    приложения логи пустые, фильтр не нужен

【 РЕШЕНИЕ 4: Автоскролл через scrollToIndex из virtualizer 】

ОБОСНУЙ:
  • При новом логе — если автоскролл включён, скроллим
    к последней строке
  • Использовать virtualizer.scrollToIndex(logs.length - 1,
    { align: "end", behavior: "auto" })
  • behavior: "auto" (не "smooth") — иначе при 100 логов/сек
    скролл не успевает
  • Отключается автоматически, если пользователь прокрутил
    вверх вручную (scrollTop + clientHeight < scrollHeight -
    threshold)

ПОЧЕМУ НЕ ПРОСТО scrollTop = scrollHeight:
  • virtualizer сам управляет scroll position
  • scrollToIndex учитывает виртуализацию

ПОЧЕМУ AUTO-ОТКЛЮЧЕНИЕ:
  • Пользователь листает логи вверх — хочет прочитать
  • Если автоскролл дёргает вниз — раздражает
  • Стандартный паттерн (как в DevTools, терминалах)

【 РЕШЕНИЕ 5: Фильтрация — на frontend, не на Rust 】

ОБОСНУЙ:
  • Логи уже в памяти (буфер 10 000)
  • Фильтрация в JS — 1–2ms для 10 000 записей
  • Мемоизация через useMemo — пересчёт только при
    изменении filter или logs
  • Не нужен round-trip к Rust

ПОЧЕМУ НЕ ФИЛЬТР В RUST:
  • Логи уже в frontend (пришли через events)
  • Дублирование логики
  • IPC-оверхед на каждый чих фильтра

ПОЧЕМУ НЕ В WEB WORKER:
  • 1–2ms — не стоит усложнения
  • 10 000 записей — не настолько много

【 РЕШЕНИЕ 6: Поиск — с debounce 200ms 】

ОБОСНУЙ:
  • Пользователь печатает → каждое нажатие запускает
    фильтрацию
  • На быстрой печати это 20+ фильтраций в секунду
  • Debounce 200ms → фильтрация только после паузы
  • UI остаётся отзывчивым

ПОЧЕМУ 200ms:
  • 100ms — слишком часто
  • 300ms — заметная задержка
  • 200ms — оптимально

【 РЕШЕНИЕ 7: Подсветка найденного текста 】

ОБОСНУЙ:
  • Пользователь ищет «error» — найденные фрагменты
    подсвечиваются жёлтым
  • Реализация: разбить строку на части через split
    по regex, обернуть совпадения в <mark>
  • Не использовать dangerouslySetInnerHTML
  • Компонент HighlightText принимает text + query

ПОЧЕМУ НЕ REGEX ЗАМЕНА НА HTML:
  • XSS-уязвимость
  • React не рекомендует dangerouslySetInnerHTML
  • Разбиение на массив — безопаснее и типизированнее

ПОЧЕМУ ЖЁЛТЫЙ:
  • Стандарт для подсветки поиска
  • Не конфликтует с цветами уровней (info/warn/error)

【 РЕШЕНИЕ 8: Экспорт через Tauri dialog.save + fs.writeTextFile 】

ОБОСНУЙ:
  • Пользователь кликает «Экспорт» → открывается системный
    диалог «Сохранить как»
  • Выбирает путь → Rust пишет файл
  • Экспортируются ТОЛЬКО отфильтрованные логи (то, что
    пользователь видит)
  • Формат: plain text, одна строка = один лог
  • Формат строки: [HH:mm:ss.SSS] [LEVEL] [source] message

ПОЧЕМУ НЕ ЧЕРЕЗ BROWSER BLOB:
  • В Tauri нет браузерного download
  • dialog.save + fs — стандартный путь

ПОЧЕМУ PLAIN TEXT:
  • Универсально
  • Легко читать
  • Можно grep / cat / etc.

ОПЦИОНАЛЬНО (если время):
  • Экспорт в JSON (с метаданными)
  • Выбор формата в диалоге

【 РЕШЕНИЕ 9: Копирование строки по клику 】

ОБОСНУЙ:
  • Пользователь кликает на строку → она копируется в
    буфер обмена
  • Показать toast «Скопировано» на 1.5 сек
  • Использовать navigator.clipboard.writeText
  • В Tauri работает (Chromium-based WebView)

ПОЧЕМУ ПОЛЕЗНО:
  • Отладка: скопировать ошибку и вставить в поиск
  • Отправить другу
  • Логирование багов

【 РЕШЕНИЕ 10: Виртуальная высота строки — 24px фиксированная 】

ОБОСНУЙ:
  • 24px = комфортно для чтения моноширинного текста 12px
  • Фиксированная высота = быстрая виртуализация
  • Перенос строк НЕ используем (см. Решение 1)
  • Длинные строки → ellipsis + tooltip

ПОЧЕМУ НЕ 28 / 32 px:
  • Больше пустого места
  • Меньше строк видно
  • 24px — стандарт для логов (DevTools, терминалы)

ПОЧЕМУ НЕ 20px:
  • Тесно
  • Моноширинный 12px требует 20+ px для комфорта

【 РЕШЕНИЕ 11: Цветовая схема уровней ]

ОБОСНУЙ:
  • info → text-primary (белый)
  • warn → amber-400 (жёлтый)
  • error → red-400 (красный)
  • success → accent-primary (неоново-зелёный)
  • debug → text-tertiary (серый)

ПОЧЕМУ НЕ ЯРКИЕ ФОНЫ:
  • Пёстро, отвлекает
  • Цвет текста достаточно
  • Фон — только для hover/выделения

【 РЕШЕНИЕ 12: Панель фильтров — sticky сверху ]

ОБОСНУЙ:
  • Пользователь скроллит логи → панель остаётся видимой
  • position: sticky, top: 0
  • Фон панели — glassmorphism с blur (чтобы не сливаться
    с логами при скролле)
  • z-index выше строк

ПОЧЕМУ НЕ ФИКСИРОВАННАЯ:
  • Фиксированная = выходит из потока
  • Sticky = часть layout, но прилипает

【 РЕШЕНИЕ 13: Счётчики по уровням в панели фильтров ]

ОБОСНУЙ:
  • Рядом с чекбоксами «info», «warn», «error» показать
    количество
  • Пример: «Error (12)» — сразу видно, есть ли ошибки
  • Обновляется при новых логах
  • Селектор useLogLevelCounts

ПОЧЕМУ ПОЛЕЗНО:
  • Быстрый обзор состояния
  • Не нужно включать фильтр, чтобы узнать число

【 РЕШЕНИЕ 14: Кнопка «Прокрутить вниз» при отключённом автоскролле ]

ОБОСНУЙ:
  • Пользователь скроллит вверх → автоскролл выключился
  • Появляется floating-кнопка «Вниз» справа снизу
  • Клик → прокрутка к последней строке + включение
    автоскролла
  • Если пользователь у конца списка — кнопка скрыта

ПОЧЕМУ FLOATING:
  • Не занимает место в панели
  • Всегда доступна

【 РЕШЕНИЕ 15: Empty state и «Логи отсутствуют» ]

ОБОСНУЙ:
  • Если логов нет:
    - «Логи пусты» + подсказка «Запустите стратегию,
      чтобы увидеть логи»
  • Если фильтр ничего не нашёл:
    - «Ничего не найдено по фильтру» + кнопка
      «Сбросить фильтры»

ПОЧЕМУ РАЗНЫЕ СООБЩЕНИЯ:
  • Пользователь понимает, в чём проблема

⚠️ ЧАСТЬ 5: ЧТО МОЖЕТ СЛОМАТЬСЯ (гипотезы)
═══════════════════════════════════════════════════════════════════════

ГИПОТЕЗА 1: Виртуализация не рендерит строки
  ПРИЧИНА: контейнер без фиксированной высоты.
  ЧТО ПРОВЕРИТЬ: parentRef должен быть на элементе с
    overflow-y-auto и известной высотой (flex-1 в
    flex-колонке).

ГИПОТЕЗА 2: Автоскролл дёргается при потоке логов
  ПРИЧИНА: scrollToIndex с behavior: "smooth" при 100
    логов/сек.
  ЧТО ПРОВЕРИТЬ: behavior: "auto" в scrollToIndex.

ГИПОТЕЗА 3: Фильтр не работает при поиске
  ПРИЧИНА: useMemo зависит от logs и filter, но filter
    мутируется вместо замены.
  ЧТО ПРОВЕРИТЬ: setFilter должен создавать новый объект.

ГИПОТЕЗА 4: Подсветка ломает регекс
  ПРИЧИНА: пользователь ввёл «.» или «(» — регекс падает.
  ЧТО ПРОВЕРИТЬ: escapeRegExp обязателен.

ГИПОТЕЗА 5: Экспорт не работает
  ПРИЧИНА: dialog.save не разрешён в capabilities.
  ЧТО ПРОВЕРИТЬ: capabilities/default.json содержит
    "dialog:allow-save" и "fs:allow-write-text-file".

ГИПОТЕЗА 6: Копирование падает с SecurityError
  ПРИЧИНА: navigator.clipboard требует secure context.
  ЧТО ПРОВЕРИТЬ: Tauri использует tauri://localhost —
    это secure context. Если падает — использовать
    @tauri-apps/plugin-clipboard-manager.

ГИПОТЕЗА 7: Toast накапливается (несколько при быстром
   копировании)
  ПРИЧИНА: setTimeout не очищается.
  ЧТО ПРОВЕРИТЬ: clearTimeout при новом копировании.

ГИПОТЕЗА 8: Панель фильтров перекрывает логи при sticky
  ПРИЧИНА: неправильный z-index.
  ЧТО ПРОВЕРИТЬ: z-10 для панели, z-0 для списка.
    Фон панели — backdrop-blur + bg-bg-primary/80.

ГИПОТЕЗА 9: Счётчики в фильтрах не обновляются
  ПРИЧИНА: селектор не подписан на logs.
  ЧТО ПРОВЕРИТЬ: useLogLevelCounts подписан на
    state.logs.

ГИПОТЕЗА 10: Поток 1000 логов/сек убивает UI
  ПРИЧИНА: батчинг в useLogsStore не работает.
  ЧТО ПРОВЕРИТЬ: flush раз в 100ms или при 50 записях
    (см. Этап 4).
